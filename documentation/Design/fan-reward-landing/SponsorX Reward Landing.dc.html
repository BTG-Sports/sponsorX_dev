Note — consent

The consent sits above the button and below the field, so it is physically in the path between typing and tapping — not under the button where a thumb never travels, and not behind a link. It’s an outlined accent panel, the only one on the page, so it reads as content rather than fine print.

Four sentences, each answering a question a stranger actually has: who gets my address, can I get out, what’s kept, who doesn’t get it. The fourth line exists because a fan may reasonably assume scanning an athlete’s code emails the athlete. Naming the sponsor as the recipient in the first line is the whole point — “our partners” would not be consent.

The button label carries the verb — “Agree and get my code” — so the affirmative act and the reward are the same tap, and the copy under it states plainly that nothing was pre-selected. A required unticked checkbox variant is available via the Consent pattern tweak when legal wants a separate recorded affirmative; it costs a second tap, and works without JS either way (native required).

Only an email field, labelled and typed email with autocomplete so the keyboard and autofill do the work one-handed. The reward recap stays pinned at the top: the fan should never have to go back to remember what they’re trading an address for.

Across all states

One template, one status slot. Document order is wordmark → status → what the reward is → action, so a screen reader reaches the offer before any chrome and the primary action is always last in the flow and inside the first screen at 390×844. Tap targets are 58px; the field is 56px; the only focus style is a 2px blue ring at 3px offset. Body copy runs at 14–15px in white at 70% or better on #0A0C10 (≈9:1) — white at 40% appears only in the simulated status bar, never in content.

Checked against the built route (src/app/r/[token]/page.tsx, rcfworks/sponsorX_dev@main). The ground here is now the route’s own two-stop wash verbatim — linear-gradient(160deg, rgba(46,155,245,.18), transparent 55%) over linear-gradient(320deg, rgba(249,122,31,.12), transparent 50%) on #0a0c10 — not an approximation, so the artboards and the live page share one background. The wordmark, the BTG · Fan reward eyebrow at .2em tracking, and the muted-text opacity steps match the route’s text-on-media/70 / /50 / /40 ladder. Body copy is lifted to 14–15px against the route’s 10–11px chrome: at arm’s length in a dark venue those sizes are the one thing in the built page that does not hold up. Each state stays a hand-rolled server render with no component imports and no client island, per the route’s own header comment.

The /t/[code] redirect stays exactly as built: SCAN is a 302, never a page, so nothing in these boards depends on it rendering. The four-step SCAN → LANDING → CLAIM → REDEEM list in the current placeholder is deliberately gone — it explains the product’s funnel to someone who only wants a coffee. The state itself is the position in the funnel. Single-use language on 1c and 1e is written to match the partial unique index on RewardEvent(tokenId) WHERE type = 'REDEEM': the page states the constraint in plain words rather than reporting it as an error.

Brand palette, dark-only ground, radial wash and the system font stack come from the brief’s hard constraints and override Nocturne’s blurple accent and Inter loading; Nocturne’s structure carries everything else — 8px radii, the fade-to-transparent rules, compact density, flush-left asymmetric layout, tinted-ramp surfaces over saturated fills. The one deliberate departure is the solid blue primary button instead of Nocturne’s accent outline: this is the only unauthenticated, one-handed, bad-light surface in the product, and an outlined CTA does not hold up in a dark venue.
