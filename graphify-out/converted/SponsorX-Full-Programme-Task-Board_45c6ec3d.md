| HOW TO READ THIS WORKBOOK |  |  |  |  |  |  |
| One sheet per phase | Phase 1–4, identical 18 columns, so they behave the same way. |  |  |  |  |  |
| Task IDs | Phase 1: P{stage}-{CAT}-{nn}, e.g. P4-BE-03. Phases 2–4: {phase}S{sprint}-{CAT}-{nn}, e.g. 2S5-BE-04 = Phase 2, Sprint 5, Backend, task 04. IDs never change — cite them in branches and commits. |  |  |  |  |  |
| Order | A dependency-respecting sort key, recomputed whenever tasks are added. It can shift; the ID cannot. |  |  |  |  |  |
| Status | Phase 1 is live. Every Phase 2–4 task starts Blocked because Phase 1 must finish first. |  |  |  |  |  |
| Weight | S=1 · M=3 · L=5 person-days. Estimates for one person, not calendar commitments. |  |  |  |  |  |
| PHASE OVERLAP |  |  |  |  |  |  |
| Permitted | Begin Phase 3 warehouse and event modelling during the final 4–6 weeks of Phase 2. Begin the Phase 4 API contract and placement taxonomy during the final 4 weeks of Phase 3. |  |  |  |  |  |
| Forbidden | No ML pricing before clean history exists — launch Phase 3 on rules. No marketplace payouts before commission snapshots, reconciliation, refunds/disputes and audit logs are tested. No virtual impressions reported to sponsors before viewability and de-duplication are validated against pilot telemetry. |  |  |  |  |  |
| SCOPE REALITY |  |  |  |  |  |  |
